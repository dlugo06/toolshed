# mind 0.1.0: a cross-machine preference store for the owner

Date: 2026-09-11
Status: approved design, pending owner review of this document
Plugin: `plugins/mind` in the `toolshed` marketplace

## 1. Purpose

`mind` is the owner's engineering memory: principles, preferences, decisions,
procedures, gotchas, and references, both universal and per project. Agents
consult it before asking the owner, apply what it says, and cite the note ID.
It works on every machine and in cloud agent sessions, so the content cannot
live in this public repo or in a per-machine file.

Split:

- **Code** lives here, in `plugins/mind`, owner-agnostic, configured by
  environment variables. Public.
- **Content** lives in a private git repo the owner controls (the "data
  repo"). The plugin clones it, reads it at session start, and writes to it
  through `/mind:remember`. Git is the sync channel, the history, and the
  review surface.

0.1.0 is the smallest usable version: inject at session start, remember, ask,
and a first population from the owner's existing documents. Passive capture,
digest, review, lint, stack skills, and stage maps are later versions.

## 2. Data repo layout

```
<data repo>/
  schema.md                     frontmatter contract and note-writing rules
  global/
    index.md                    generated from global/notes, never hand-edited
    notes/<ID>-<kebab-title>.md
  projects/
    index.md                    generated: one line per project
    <slug>/
      project.md                purpose, repo URL, stack, aliases, related projects
      index.md                  generated from projects/<slug>/notes
      notes/<ID>-<kebab-title>.md
```

Only note files and `project.md` are authored. Every `index.md` is regenerated
by the script after each write, so concurrent sessions on different machines
never edit the same hot file; a conflict can only occur when two sessions add
the same note filename, which the ID assignment makes rare and the sync retry
resolves. Git history is the change log; there is no `log.md`.

`project.md` frontmatter:

```yaml
---
slug: erp-quotes            # matches the folder name
name: ERP quote automation
repo: git@github.com:owner/erp-quotes.git
stack: [python, postgresql, playwright]
aliases: [erp-quotes-old, /Users/owner/Code/quotes]   # other origin names or paths
related: [toolshed]
updated: 2026-09-11
---
One paragraph: what the project is and what kind of work it involves.
```

`projects/index.md` is one line per project: slug, name, stack, the first
sentence of the body. It is always injected, so any session knows the other
projects exist and where to look.

## 3. Note schema

```yaml
---
id: PREF-REV-003
title: Never auto-approve during process-review
type: preference      # principle | preference | decision | procedure | gotcha | reference
stage: review         # identity | product | planning | development | testing | review | release | deployment | monitoring | security
scope: global         # global | project:<slug>
strength: must        # must | should | default | optional
status: accepted      # draft | accepted | superseded | deprecated
affirmed: 2026-09-11  # last date the owner confirmed it
supersedes: null      # ID of the note this replaces, if any
source: CLAUDE.md, erp-quotes, 2026-09-11   # where the claim came from
---
One or two sentences stating the claim.

**Why:** the reason, with the incident or evidence if there is one.
**How to apply:** what an agent does differently because of this note.
**Related:** [[PREF-REV-004-do-not-resolve-pr-threads]]
```

Type semantics (from the 2026-09-06 research):

- **principle**: always true, MUST or MUST NOT.
- **preference**: default choice when several are valid; applied without asking.
- **decision**: dated record with context, options, rationale, consequences; superseded, never edited.
- **procedure**: a checklist.
- **gotcha**: a trap with the evidence that proved it.
- **reference**: URLs, IDs, dashboards.

ID scheme: `<TYPE>-<STAGE>-<NNN>`, with type codes PRIN, PREF, DEC, PROC,
GOT, REF and stage codes ID, PROD, PLAN, DEV, TEST, REV, REL, DEPLOY, MON,
SEC. Numbers are assigned per scope folder, so a project note is cited with
its slug: `erp-quotes/GOT-DEPLOY-004`. A global note is cited bare.

Status semantics: only `accepted` notes appear in injected indexes. `draft`
notes are counted in the injection ("N drafts await acceptance") and listed
by `/mind:ask --drafts`. `superseded` and `deprecated` notes stay on disk
for history and never inject.

Required fields on `add`: `title`, `type`, `stage`, `strength`. Defaults:
`status: accepted`, `affirmed: today`, `scope` from the `--scope` flag,
`source: session <date>, <slug>`. The script rejects unknown enum values.

## 4. Configuration and project identity

Environment variables, all read by the script:

| Variable | Required | Meaning |
|---|---|---|
| `MIND_REPO` | yes | git URL of the data repo (ssh or https). Unset means the plugin is inert. |
| `MIND_HOME` | no | checkout path. Default `${CLAUDE_PLUGIN_DATA}/repo`, falling back to `~/.mind/repo` when the plugin-data variable is absent. |
| `MIND_TOKEN` | no | token for https remotes (cloud sessions). Supplied to git through a credential helper at call time; never written to disk. |
| `MIND_PROJECT` | no | force the project slug for this session. |

Project slug resolution, first match wins:

1. `MIND_PROJECT`.
2. The last path segment of `git remote get-url origin`, without `.git`, lowercased.
3. The basename of the git top-level directory.
4. The basename of the current directory.

The candidate is then matched against every `projects/<slug>/project.md`
by `slug` and by `aliases`. If nothing matches, the session has no project
folder: injection says so and still prints the projects index; the first
`/mind:remember --scope project` creates `projects/<candidate>/` with a stub
`project.md` the agent fills in from the repo's own `CLAUDE.md` or README.

## 5. Session start

`hooks/hooks.json` registers a SessionStart command hook on
`startup|resume|clear|compact` running `scripts/session-start.sh`, which
exits 0 when `MIND_REPO` or `python3` is missing and otherwise runs
`python3 scripts/mind.py inject --event <matcher>`.

`inject`:

1. If the checkout is missing, clone it (30 s timeout). On failure print one
   line ("mind: clone failed, <reason>") and exit 0.
2. On `startup` and `resume`, pull fast-forward (10 s timeout). On failure
   print "mind: offline, using cached copy from <date of HEAD>" and continue.
   On `clear` and `compact`, do not touch the network.
3. Print, in order:
   - the protocol (below),
   - `global/index.md`,
   - the current project's `index.md`, or "no notes for <candidate> yet",
   - `projects/index.md`,
   - the draft count when non-zero.
4. Budget: indexes together are capped at 4,000 characters. Truncate the
   global index first, then the project index, never the projects index, and
   end a truncated section with "+N more, run /mind:ask <topic>".

The protocol text:

> Mind: the owner's preferences. Notes at `<MIND_HOME>`. Before asking the
> owner a question, run `/mind:ask <topic>`. If a note answers it, apply it
> and cite the ID. If none does, ask once, then `/mind:remember` the answer:
> universal facts go to global, facts about this repo go to the project. When
> this project is silent, look in related projects' notes. If two notes
> conflict, surface both IDs and ask. The project's own `CLAUDE.md` wins over
> any note. Save memories through `/mind:remember`, not the auto-memory
> directory.

## 6. Skills and script

One script, `scripts/mind.py`, stdlib only, with subcommands. Skills are thin
wrappers that tell the agent when and how to call it.

| Subcommand | Does |
|---|---|
| `inject --event E` | section 5 |
| `add <draft.md> --scope global\|project [--project slug]` | validate frontmatter, assign ID, write the note, reindex, commit `mind: add <ID> <title>`, sync, print the ID and sync outcome |
| `ask <terms...> [--all] [--project slug] [--drafts]` | case-insensitive term match over title and body of accepted notes in global plus the current project (`--all`: every project); rank by terms hit; print up to 10 rows `ID | title | scope | strength` each followed by the note's first paragraph |
| `reindex` | regenerate every `index.md` from notes; used by `add` and by hand after manual edits |
| `accept <ID>` | set `status: accepted` and `affirmed: today`, reindex, commit, sync |
| `sync [--pull-only]` | pull with rebase when local commits exist, else fast-forward; push when ahead; one retry on push rejection |

Skills:

- **`remember`** (`/mind:remember`): the agent drafts the note in the
  scratchpad following `schema.md`, chooses the scope by the test "would this
  be true in a different repo", runs `ask` first to avoid a duplicate or to
  find the note it supersedes, then runs `add`. Reports the ID and whether the
  push succeeded.
- **`ask`** (`/mind:ask <topic>`): runs `ask`, reads the full note files for
  any hit that matters, and answers with the IDs cited. With no hit, says so
  and, when a related project exists, retries with `--all`.

## 7. Git sync and error handling

- Authentication: SSH on the owner's machines. In cloud sessions `MIND_REPO`
  is an https URL and `MIND_TOKEN` is set; the script passes a credential
  helper on the git command line (`-c credential.helper=...`) that echoes the
  token, so it never lands in `.git/config` or a file.
- Timeouts: clone 30 s, pull 10 s, push 20 s.
- The hook never blocks a session: every failure path prints one line and
  exits 0.
- `add` writes the note and commits before any network call. A failed push
  leaves the commit local and prints "mind: push failed, note is committed
  locally; it will push on the next remember or session start". The next
  `add` or `inject` runs `sync` and retries the push.
- `sync` conflict on rebase (same filename added twice): abort the rebase,
  rename the local note to the next free ID, reindex, commit, retry once.

## 8. First population (seeding)

The mind is only useful once it holds what the owner has already written
down. Seeding reads every document that says how the owner wants work to
work, not only the auto-memory files. Source groups, per project the owner
names:

1. Global Claude Code configuration: `~/.claude/rules/*.md`, user-level
   skills, user-level hooks in `settings.json`.
2. Auto-memory directories under `~/.claude/projects/*/memory/`.
3. Project instruction files: `CLAUDE.md`, `.claude/rules/`,
   `.claude/settings*.json` hooks, hookify rule files.
4. Project guideline documents: development, testing, security, monitoring,
   architecture, anti-detection, and similar docs the project keeps for agents.
5. Product records: PRD phase files and the deferred-decisions file, for
   decisions and rulings, not for task lists.
6. Design specs and implementation plans, for decisions and precedence
   rulings that a spec recorded.
7. Agent reports and retros: review reports, security and silent-failure
   reviews, session notes, incident write-ups, for gotchas and for
   preferences the owner stated in rulings.
8. This marketplace's own reference documents and changelog, for the
   workflow rules the plugins encode.

Method:

- One extraction subagent per source group, briefed with `schema.md`, the
  scope test, and the rule "run `ask` before every `add`; supersede, never
  duplicate". Each writes notes through `add` and returns a table of IDs.
- Status on import: an explicit directive in a curated instruction file
  (groups 1, 3, 4, 8) imports as `accepted`. A preference inferred from a
  report, retro, or spec (groups 5, 6, 7) imports as `draft` for the owner to
  accept. Every note carries `source`.
- A group of memory files that already has `**Why:**` and `**How to apply:**`
  lines keeps them verbatim.
- No secret ever becomes a note: no token, password, DSN key, or credential
  value. A `reference` note may say where a secret lives, never what it is.
  The extraction brief says so and the controller greps new notes for
  key-like strings before accepting the batch.
- After seeding, the controller runs `ask` for ten questions the owner has
  answered before this week and checks each is answered by a cited note.
- Auto-memory directories stay in place, read-only by convention, until the
  owner confirms the mind covers them. Removing them is a separate decision.

The concrete inventory of files per project is personal and lives outside
this repo.

## 9. Testing

`plugins/mind/tests/test_mind.py`, pytest, run with the same command as the
orchestrator tests. Git operations run against a bare repo created in
`tmp_path`, with `MIND_REPO` and `MIND_HOME` pointed at temp paths. Cases:

- slug resolution: env override, origin URL, git top-level, cwd, alias match.
- `add`: ID assignment per scope, filename, enum validation, defaults,
  rejected unknown fields, project folder creation with stub `project.md`.
- `reindex`: grouping by stage, drafts excluded, projects index line format.
- `inject`: order of sections, budget truncation order, draft count, missing
  project message, offline fallback line, `compact` makes no network call.
- `ask`: ranking, `--all`, `--drafts`, no-hit output.
- `sync`: push after add, retry on a rejected push, rebase conflict rename.
- hook script: no `MIND_REPO` prints nothing and exits 0.

Every assertion checks concrete values (the exact ID, the exact line).

- `plugins/mind/.claude-plugin/plugin.json` and the marketplace entry go to
  `0.1.0`; `CHANGELOG.md` entry; root `README.md` and `plugins/mind/README.md`
  describe the env vars, the two skills, the data repo layout, and setup:

  ```sh
  claude plugin install mind@toolshed
  export MIND_REPO=git@github.com:<owner>/<data-repo>.git
  ```

- Public-repo check before commit: no personal names, local paths, or
  references to the owner's other projects in the diff.
- After 0.1.0 is installed on the primary machine and seeded: verify on a
  second machine or fresh clone, then in a cloud session, where the open
  question is whether outbound git to a second private repo is allowed.
  That check gates nothing in 0.1.0 itself.
